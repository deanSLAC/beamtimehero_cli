00 Status — implemented

This plan was executed on 2026-09-04. The sections below are kept as the rationale; this one records what actually landed and where it diverged.

Done 218 tests green

science/ exists with 35 modules across the seven directories. Every old module path is a re-export shim, so the five consuming apps are untouched — and because the test suite still imports through the old paths, those 218 passing tests are themselves the shim-compatibility check (the baseline was 212).

The duplicated science is gone from the handler layer: tools_core.py now calls xas_policy.white_line_components_for(), xas_policy.window_rel_from_absolute(), xas_policy.resolve_edge(), xas_policy.check_overlap() and the ex_policy.DEFAULT_* constants — 8 and 11 call sites respectively, each previously a hard-coded copy.

Audited after the move: no code under science/ reads an environment variable, opens a file, imports config, touches SPEC, or imports argparse — and science/ imports nothing outside science/. The rule holds mechanically, not just by intent.

Diverged from the plan, with reasons 5 items

1. normalize_series and edge_step_normalize went to reduce/normalize.py, not to reduce/reps.py and xas/normalize.py as drafted. Splitting normalize_series from the edge_step_normalize it delegates to would have created a backwards reduce → xas dependency. Both are per-scan monitor normalization — the stage before technique-specific work — so they belong together, and the rigorous XAS normalizations (area, MBACK, Athena-style) keep xas/normalize.py to themselves.

2. A second violation of the rule turned up during the move. pick_active_counter read BTH_ACTIVE_COUNTER_PRIORITY from the environment. The env read moved to config.active_counter_priority() and the counter priority is now passed in as an argument. That variable is set by autonomous_fourone, and no app calls pick_active_counter directly, so the four spec_data call sites now supply it and the override behaves exactly as before.

3. fitting/ holds only similarity.py — generic_data/fitter.py stays unrouted, as you asked. The directory exists so the eventual home is obvious.

4. plots/ holds xas.py and scan.py. The spec_data/*_plotting.py split was an open question and was left alone.

5. calibration_store.py moved up a layer to beamtimehero_cli/calibration_store.py. It writes a JSON file to a configured directory — session state, not science.

src/beamtimehero_cli/science/README.md — the rule, the layout, the "you want to change X → go to Y" table, the conventions (citations, provenance, degrade-don't-crash), and the moved-from map. 01 Why the science is hard to find today

Four navigation problems, all fixable by moving files. None of them is about code quality — the functions themselves are good.

The three directory names don't describe their contents naming

Science currently lives in analysis/, interpretation/ and generic_data/. Nothing about those names tells a scientist which one holds edge-step normalization, which holds the χ(k) Fourier transform, or which holds the Compton subtraction. Worse, the split between them is by abstraction level — raw math vs. verdict-forming vs. technique-agnostic — which is a programmer's axis. A scientist navigates by technique first, then pipeline stage: "XAS → normalization", "XRS → background", "EXAFS → Fourier transform."

One technique's code is split across two dirs, inconsistently structure

XAS math is in analysis/xas.py and spread over nine unprefixed files in interpretation/ (normalize, descriptors, edges, quality, interpret, calibrations…). XRS code in the same directory is prefixed (xrs_descriptors, xrs_edges, xrs_interpret). So the convention is "XRS is labelled, XAS is whatever's left" — you have to already know that to read the directory.

analysis/xas.py is two unrelated modules in one file structure

Half of it is detector- and scan-level reduction that has nothing to do with XAS — pick_active_counter, average_reps, filter_short_reps, estimate_per_rep_noise, deadtime_correct. Those apply equally to XRS and EXAFS. The other half is genuinely XAS — edge_step_normalize, align_spectra, difference_spectrum. A scientist working on Raman has to read an XAS file to find the rep-averaging they need.

Real scientific decisions live in the tool handler file the important one

tool_catalog/tools_core.py is 2,931 lines of glue — and it contains policy that is unambiguously science, in several cases duplicated, because each handler needed it independently. A scientist who wants to change any of these has to go into the toolbelt machinery and find every copy:

The Ce(IV)-doublet / U(VI)-satellite rule — 3 if family in ("ln_L3","an_L3","an_M") else 1 — appears verbatim at lines 1240 and 1544.
The pre-edge window absolute→relative conversion at 1245 and 1506, and the window re-derived again at 1603.
The default EXAFS k-weight of 2 hard-coded at 2386, 2450, 2491, 2525, 2564 — five copies.
The element/edge auto-detection policy — explicit-vs-auto branching, E₀ anchoring, ambiguity flagging — in _interpretation_inputs (1195–1225), with only the scoring in interpretation/edges.py.
The "≥20 overlapping points" data-adequacy rule at 1181.
Convergence targets sem_threshold_frac=0.01, drift_threshold_frac=0.01 at 715–716.
And seven handlers do raw numpy math inline — t_compare_xas_to_references, t_difference_spectrum, t_align_crystals, t_sum_crystals, t_tag_crystal_q, t_extract_chi, t_compare_xrs_to_references.

02 The one rule

Everything below follows from a single sentence. It is the thing to put at the top of the science directory, and it is already ~95% true of the existing code — so this is mostly formalising a boundary you've been respecting by instinct.

Everything under science/ takes numbers in and returns numbers out. No file paths, no environment variables, no SPEC, no database, no argparse.

The corollaries are what make it usable as a routing rule. If your function needs to know where the data lives → it belongs in spec_data/. If it needs to know what the agent asked for → it belongs in tool_catalog/. If it takes arrays and returns a dict of numbers, it is science and it goes here, no matter which technique it serves.

That rule is checkable at a glance from the function signature alone, which is the property that matters. A collaborator never has to ask permission or trace imports to know whether they're in the right place.

There is exactly one place the existing code violates it: interpretation/calibration_store.py reads beamtimehero_cli.config to find a directory to write a JSON file into. That's session state, not science — it moves up a layer, or takes the directory as an argument. Everything else in analysis/, interpretation/ and generic_data/ already obeys the rule.

Four decisions worth calling out

  • tables/ separates data from algorithms. Edge energies, per-element edge shifts, core-hole widths, valence spans, emission lines, XRS edge assignments — these are the things a scientist most often wants to correct or extend, and they need no code reading at all. Today they're scattered across four files that also contain fitting logic. Pulling them into one directory of pure, cited tables makes the most-editable content the most findable content.
  • reduce/ holds what isn't technique-specific. Counter selection, rep averaging, dead-time, glitch and saturation detection. This is the half of analysis/xas.py that was never about XAS, plus interpretation/quality.py. Naming it reduce/ says what stage it is, and its absence from xas/ says it applies to everything.
  • policy.py per technique is the new idea. Every scientific default and heuristic currently embedded in the handler file gets a name, a home and a citation: DEFAULT_KWEIGHT, white_line_components_for(family), pre_edge_window_for(e0, …), autodetect_edge(...), MIN_OVERLAPPING_POINTS. This is where the biggest iteration win is — see §04.
  • fitting/ is deliberately not spectroscopy. generic_data/fitter.py is knife-edge, aperture and emission-peak fitting for beam diagnostics and alignment. Grouping it with the spectroscopy would mislead; giving it its own named directory tells a scientist "this is alignment maths, not your XANES."

04 Getting the science out of the handler file

This is the part that actually changes what iteration feels like. The moves in §03 are bookkeeping; this one removes the reason a scientist ever has to open tools_core.py.

The handler layer's only job should be: unpack the argument dict, ask spec_data for arrays, call one science function, serialise the result. Where it currently makes a scientific choice, that choice moves into a policy.py and the handler calls it by name. Concretely: 

# today — tools_core.py, twice (1240 and 1544), inside 2,931 lines of glue
wl_comps = int(arguments.get("white_line_components") or 0)
if wl_comps <= 0:
    wl_comps = 3 if edge_info["family"] in ("ln_L3", "an_L3", "an_M") else 1

# after — science/xas/policy.py, once, findable and citable
# Ce(IV) shows a final-state L3 doublet and U(VI) M4 carries satellites, so
# these families need a multi-component white line. Bugarin & Glatzel 2024;
# Bes et al. 2016.
MULTI_COMPONENT_FAMILIES = ("ln_L3", "an_L3", "an_M")

def white_line_components_for(family: str) -> int:
    return 3 if family in MULTI_COMPONENT_FAMILIES else 1

# and the handler becomes a single line with no scientific opinion in it
wl_comps = arguments.get("white_line_components") or policy.white_line_components_for(family)

Same treatment for the five copies of kweight=2, the pre-edge window conversion, the ≥20 points adequacy rule, the convergence targets, and the element/edge auto-detection policy in _interpretation_inputs — which is the largest single piece, and the one with an actual physics argument in its comment (E₀ anchoring, because the window one-third-point proxy misranks Ni K against Er L3). That comment is scientific reasoning and it should not be buried in a private helper in the glue layer.

The seven handlers doing inline numpy get the same treatment: the LCF residual RMSE in t_compare_xas_to_references, the crystal interpolation in t_align_crystals and t_sum_crystals, the peak search in t_tag_crystal_q. Each is a few lines, each becomes a named function in the matching science/ module.

Once that's done there's a clean statement you can make to a collaborator, which is worth more than any of the individual moves: if you're editing a file outside science/, you're probably in the wrong place.

05 What you actually hand a collaborator

Four artifacts. The layout above is only useful if someone is told about it, and the last one keeps that telling from going stale.

  1. science/README.md — the rule and the map

    Opens with the one rule from §02, then the routing table: a scientist arrives with a question, and the table answers it in one hop. This is the whole onboarding document; it should stay under two screens.

    You want to change…Go to
    an edge energy, core-hole width, or edge-shift slopescience/tables/
    which counter is picked, or how reps are averagedscience/reduce/
    how μ(E) is normalized (area, edge-step, MBACK)science/xas/normalize.py
    how E₀ is found, or the pre-edge / white-line fitsscience/xas/e0.py · fits.py
    how an oxidation state or geometry verdict is reachedscience/xas/interpret.py
    a default window, k-weight, or auto-detection rulescience/<technique>/policy.py
    χ(k) extraction, background, or the Fourier transformscience/exafs/
    the energy-loss axis, Compton background, or crystal summingscience/xrs/
    a knife-edge / aperture / emission-peak fit for alignmentscience/fitting/
    what a plot looks likescience/plots/

  2. CONTRIBUTING.md — and one honest paragraph about what not to touch

    Short, and pointed at science/README.md for anything scientific. The one thing it must say plainly: the files that define what the agents see are tool_catalog/definitions.py, tool_catalog/categorize.py and cli/. Changing a tool's name, its parameters, or which branch it sits on changes what five separate applications see, so those are the files to raise rather than edit.

    Everything inside science/ is fair game — and it's worth saying that explicitly, because the default assumption in a repo this dense is that nothing is safe to touch. Naming the small off-limits set is what makes the large safe set usable.

  3. A generated science index, next to the tool catalog

    docgen.py already renders docs/tool_catalog.html from the live registry, which is why that page can't drift. Point the same machinery at science/ and emit docs/science_index.html: every function, its signature, the first line of its docstring, its citations, and which tools call it.

    That last column is the one that makes the science "directly identifiable" in the sense you asked for — a scientist reading fit_white_line can see it backs extract_xas_descriptors and interpret_oxidation_state, so they know what their change affects without tracing imports. And because it's generated by walking the package, a new function appears on the page by existing.

  4. A citation convention, since you're already 80% doing it

    The code already carries AREA_NORM_CITATION, MBACK_CITATION, EDGE_ENERGY_SOURCE, CORE_HOLE_WIDTH_SOURCE, and inline references to Wilke 2001, Bugarin & Glatzel 2024, Weng & Penner-Hahn 2005, Bes 2016. Make it uniform: every module under science/ declares a module-level CITATIONS dict, and docgen collects them into a bibliography on the index page.

    This is a small thing that does disproportionate work with scientific collaborators — it makes the directory read like a methods section, and it gives someone adding a new method an obvious slot to justify it in.

06 How the move avoided breaking the apps

Five applications import from this package as sibling checkouts, several of them reaching directly at analysis/ and interpretation/ module paths. So the moves had to be non-breaking: every old module stayed in place as a re-export shim. These are generated from the new modules' public names, so they cannot silently omit a symbol. 

# analysis/xas.py — after the move
"""Moved to science/. Kept as a shim so existing imports keep working."""
from beamtimehero_cli.science.reduce.counters import pick_active_counter, counter_selection_warning
from beamtimehero_cli.science.reduce.reps import average_reps, filter_short_reps, estimate_per_rep_noise
from beamtimehero_cli.science.xas.normalize import edge_step_normalize
from beamtimehero_cli.science.xas.compare import align_spectra, difference_spectrum

That makes the whole reorganisation a pure addition from every consumer's point of view — nothing downstream has to change on the same day. Then update the in-repo callers (tools_core.py and spec_data/) to the new paths, migrate the apps whenever convenient, and delete the shims once they're unused. The policy.py extraction in §04 is independent and can happen before or after; it touches only tools_core.py, which no app should be importing from anyway.

Sequencing suggestion, if it helps: tables/ first (pure data, zero risk, and immediately the most useful thing for a collaborator), then reduce/ (breaks up the mixed xas.py), then the three technique directories, then policy.py last since it's the only step that changes behaviour boundaries rather than just locations.

Open questions

  • generic_data/fitter.py and experiment_planning/decisions.py — in or out? Together that's about 1,600 lines of fitting and decision logic that nothing currently imports (fitter.py is reachable only through decisions.py, which has no callers). It's also the most scientific-looking code in the repo, so it's where a new collaborator will gravitate first. Either wire it up under science/fitting/ or delete it — leaving it in place unrouted will cost every newcomer a day.
  • Does experiment_planning/ belong under science/? scan_features.py and scan_efficiency.py are live and array-shaped, so by the rule in §02 they qualify — probably as science/planning/. But the README currently claims experiment-planning lives in consuming projects, so the intent here needs settling before it gets a home.
  • Should spec_data/*_plotting.py split? Those files mix file-name-taking figures with array-taking figures. The rule sorts them cleanly, but it's a handful of functions to reassign and worth confirming you want the churn.
